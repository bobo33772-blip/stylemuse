# StyleMuse 프로토타입 — 수정 기록

작성일 2026-09-09 · 대상 저장소 `AI 사업2` · 프로젝트 StyleBridge (Supabase)

---

## 1. 개요

### 수정 전 상태

핀터레스트 해외 코디를 국내 아이템으로 매칭해주는 웹 프로토타입이었다. Flask가 HTML 세 장을 서빙하고, 브라우저가 Supabase에서 코디를 읽어 갤러리로 뿌리는 구조였다. AI 분석 기능은 화면에 버튼까지 있었지만, 실제로는 **브라우저가 OpenAI를 직접 호출**하고 있었고 그 API 키가 `static/config.js`에 그대로 적혀 모든 방문자에게 전송되고 있었다. 분석 결과는 화면에만 잠깐 뜨고 DB에 저장되지 않아 새로고침하면 사라졌다. 서버에서 분석·저장을 처리하도록 설계된 Edge Function 파일이 저장소에 있었지만 **어디에서도 호출하지 않았고, 배포된 적도 없었다.** 관리자 업로드 화면은 변수 이름 충돌로 열자마자 오류가 나서 한 번도 동작한 적이 없었다.

### 이번 수정의 목적

크게 세 단계였다. 먼저 **API 키 노출을 없애고 AI 분석이 실제로 동작하며 결과가 남도록** 만들었다. 다음으로 **매칭 정확도와 호출 비용**을 다뤘다. 마지막으로 **화면을 MVP 시연 형태로 정리**하고, 사람이 매칭 근거를 직접 입력하는 운영 화면을 붙였다. 진행 중 발견한 데이터 삭제 사고와 보안 문제는 별도로 기록했다.

### 2-1. AI 분석 경로를 브라우저에서 서버로 이전

| 항목 | 내용 |
|---|---|
| 무엇 | 브라우저가 OpenAI를 직접 부르던 것을 Supabase Edge Function 호출로 교체. 분석 결과를 DB에 저장하고 화면에 반영 |
| 왜 | `config.js`에 실제 OpenAI 키가 적혀 있어 방문자 누구나 복사해 쓸 수 있었다. 분석 결과가 저장되지 않아 매번 다시 분석해야 했다. 저장까지 처리하도록 만들어진 Edge Function이 호출되지 않고 방치돼 있었다 |

### 2-6. 검색 결과 캐시와 상품 재사용

| 항목 | 내용 |
|---|---|
| 무엇 | 검색어와 상품을 DB에 기억해 같은 검색어는 외부 API를 다시 부르지 않도록 변경 |
| 왜 | 외부 검색 API가 무료 250회/월인데 코디 1건 분석에 6~9회를 썼다. **정확도보다 비용 한도가 먼저 벽에 부딪힐 상황**이었다. 원래 계획은 구글을 거치지 않고 무신사를 직접 검색하는 것이었으나 아래 사유로 불가능해 방향을 바꿨다 |
| 파일 | `supabase/functions/analyze-look/index.ts`, `supabase/migrations/20260909000000_search_cache.sql` |
| 결과 | 같은 코디 재분석 기준 **20~50초 → 8초, 외부 API 6회 → 0회** |
| 부수 효과 | 이 과정에서 데이터 삭제 사고를 발견했다(4-1). 캐시로 쌓이는 상품 테이블은 향후 이미지 검색용 카탈로그의 출발점이 된다 |

> **무신사 직접 검색이 불가능한 이유** — `robots.txt`가 검색엔진·AI 봇을 제외한 모든 자동 접근을 금지한다(`User-agent: * → Disallow: /`). 공식 API도 입점 브랜드용(주문 연동)뿐이고 제3자 상품 수집 경로가 없다. 확인 결과 **현재의 구글 경유가 무신사가 허용한 정당한 경로**였다. 별도로 공식 제휴 프로그램(무신사 큐레이터)의 존재를 확인했고, 상품 데이터 피드 제공 여부는 문의가 필요하다.

## 3. DB 스키마 변경

### 추가한 컬럼

| 테이블 | 컬럼 | 용도 | 비고 |
|---|---|---|---|
| `looks_items_match` | `original_type` | 원본 코디 속 아이템의 유형. 브랜드명 제외 | 기존 39건은 `null` |
| `looks_items_match` | `match_reason` | 이 상품을 고른 근거 한 줄 | 기존 39건은 `null` |
| `musinsa_items` | `sold_out` | 품절 여부 | 기본값 `false` |
| `musinsa_items` | `product_key` | 같은 상품을 같은 값으로 식별 | 캐시 도입 시 추가 |
| `search_cache` (신규 테이블) | — | 검색어와 상품의 연결 기억 | 외부 API 재호출 방지 |

### 왜 `musinsa_items`가 아니라 `looks_items_match`인가

`original_type`과 `match_reason`은 **상품의 속성이 아니라 코디와 상품 사이 관계의 속성**이다. 같은 상품이 여러 코디에 매칭될 수 있고, 그때 "원본 사진 속 어떤 옷을 대체하는가"와 "왜 이 상품인가"는 코디마다 달라진다. 상품 쪽에 두면 한 코디에서 쓴 근거가 다른 코디에도 딸려가 사실과 어긋난다. 연결 테이블에 두면 각 매칭이 자기 근거를 갖는다.

`product_key`는 반대로 상품 고유의 값이라 `musinsa_items`에 뒀다. 구매 링크에 요청마다 바뀌는 추적 파라미터가 붙어 URL만으로는 같은 상품을 식별할 수 없었기 때문에 별도 식별자가 필요했다.

### 마이그레이션 파일

| 경로 | 내용 |
|---|---|
| `supabase/migrations/20260909000000_search_cache.sql` | `product_key` 추가, 중복 상품 병합, `search_cache` 생성, 유니크 인덱스 |
| `supabase/migrations/20260909010000_match_context_and_sold_out.sql` | `original_type`, `match_reason`, `sold_out` 추가 |

두 번째 파일은 요청이 "작성하고 저장"까지여서 처음에는 적용하지 않았다. 이후 화면에서 새 컬럼을 조회하게 되면서, 컬럼이 없으면 갤러리 전체가 빈 화면이 되는 상황이라 함께 적용했다.

## 4. 구현 중 발견한 문제와 대응

### 4-1. 재사용하려던 상품 데이터가 삭제되고 있었다

| 구분 | 내용 |
|---|---|
| 발견 경위 | 캐시를 넣었는데 적중률이 계속 0이었다. 검색어는 매번 동일한데도 매번 새로 검색하고 상품 행이 새로 생겼다. 캐시 테이블을 직접 조회해 보니 **직전 실행이 만든 기록이 사라져 있었다** |
| 원인 | 재분석 시 "어느 코디에도 붙지 않은 상품은 쓰레기"로 보고 지우는 로직을 앞서 넣어뒀다. 캐시를 도입한 뒤에는 **그 상품들이 쓰레기가 아니라 재사용하려고 남겨둔 자산**이 됐는데 판단 기준을 바꾸지 않았다. 상품이 지워지면 연결된 캐시 기록도 연쇄 삭제됐다 |
| 조치 | 해당 삭제 로직을 제거했다. 재분석은 이제 그 코디의 연결만 끊고 상품은 남긴다 |
| 삭제 규모 | **원본 코디 15건은 손실 없음**(id 결번 0). 삭제는 AI 매칭 결과에 한정 — 상품 테이블 결번 31개, 매칭 테이블 결번 40개. 사용자 데이터나 업로드 이미지 손실은 없다 |
| 남은 흔적 | id는 재사용되지 않아 결번은 그대로 남는다. 어느 코디에도 붙지 않은 상품 3건이 현재 남아 있는데, 이는 재사용 대상이므로 정상이다 |

**배운 점** — 캐시를 도입한 순간 기존의 "쓰레기 판정" 기준이 틀린 것이 됐다. 새 기능을 넣을 때 그것이 기존 로직의 전제를 뒤집는지 확인하지 않은 것이 원인이었다.

### 4-2. 초기 화면에 표시할 데이터가 0건이었다

| 구분 | 내용 |
|---|---|
| 원인 | 초기 활성 필터를 "미니멀"로 지정했는데, DB에 미니멀 코디가 **0건**이었다. 실제 데이터는 긱시크·아메카지·고프코어 각 5건뿐이었다. 그대로 두면 첫 화면이 빈 화면이 된다 |
| 선택지 | ① 관리자 화면에서 미니멀 코디를 새로 업로드해 데이터를 만든다 ② 활성 필터를 데이터가 있는 태그로 바꾼다 ③ 기존 코디의 태그를 미니멀로 바꿔 채운다 |
| 최종 결정 | ②를 택했다. 활성 필터를 아메카지로 바꿨고, 이후 "All"을 복원해 전체를 기본으로 두고 데이터가 있는 태그만 자동 활성화하는 방식으로 정리했다 |
| 근거 | ①은 시연까지 시간이 걸리고, ③은 실제 사진이 미니멀이 아니어서 **데이터에 거짓을 넣는 셈**이라 배제했다. 이후 데이터가 늘거나 줄어도 화면이 알아서 맞도록 태그별 코디 수를 세어 판단하게 만들어, 같은 문제가 반복되지 않게 했다 |

**부수 조치** — 그래도 빈 화면이 나올 수 있는 경우를 대비해 "준비 중인 스타일이에요" 안내를 넣었다. 빈 화면은 고장인지 데이터가 없는 것인지 구분되지 않는다.

### 4-3. RLS 미적용과 관리자 인증 부재

| 구분 | 내용 |
|---|---|
| 발견 경위 | 큐레이션 화면을 만들면서 브라우저에서 DB 쓰기가 가능한지 확인하다가, 세 테이블 모두 접근 제어가 꺼져 있는 것을 확인했다. 실제로 브라우저와 동일한 자격으로 데이터를 수정하고 되돌려 보며 검증했다 |
| 위험 범위 | `pinterest_looks`, `looks_items_match`, `musinsa_items` 세 테이블에 RLS가 꺼져 있고 정책이 0개다. 브라우저 키는 `config.js`에 담겨 모든 방문자에게 전송되며 `/admin`에는 인증이 없다. **키를 확인한 누구나 코디·상품·매칭을 수정하거나 삭제할 수 있다** |
| 판단 | MVP 검증 이후로 미루기로 결정 |
| 근거 | 프로토타입 단계에서는 로컬 또는 화면 공유로만 시연한다. 외부 URL 배포 계획이 없다. 지금은 매칭 근거 데이터를 채우는 것이 우선순위다 |
| 기록 | `README.md` 상단에 「배포 전 필수 조치」로 체크리스트화. 결정 일자와 미룬 이유를 함께 남겨, 몰라서 빠뜨린 것이 아니라 의도적 판단임이 드러나게 했다 |

**배포 전 필수 조치**

- `pinterest_looks`, `looks_items_match`, `musinsa_items`에 RLS 적용
- anon 키는 SELECT만 허용
- `/admin`에 Supabase Auth 기반 인증 추가
- 쓰기 작업은 인증된 사용자 또는 Edge Function으로 제한

### 4-4. 코디·사진이 전부 안 뜨고 빈 화면만 보였다 (2026.10.26)

| 구분 | 내용 |
|---|---|
| 증상 | 앱에 들어가면 코디 목록도, 사진도 나오지 않고 빈 화면만 보였다 |
| 원인 추정 | Supabase 무료 플랜은 7일간 DB 활동이 적으면 프로젝트를 일시정지한다. 09.15 이후 사용이 거의 없어 정지된 것으로 보인다. 정지되면 DB 조회와 Storage 이미지가 함께 실패하므로 "코디도 사진도 안 뜬다"는 증상과 맞는다. 원격 대시보드는 직접 확인하지 못했다 |
| 코드 문제 | 조회가 실패하면 `console.error`만 남기고 피드를 비워 두었다. 유저는 "콘텐츠가 없다"와 "고장 났다"를 구분할 수 없었다. 또 로그인 상태 복원이 예외로 끝나면 코디 로드가 아예 실행되지 않는 구조였다 |
| 조치 | 실패 시 안내 문구와 「다시 시도」 버튼 표시. 로그인 복원 실패가 피드 로드를 막지 않게 분리. CDN의 supabase-js를 `@2`에서 `@2.118.0`으로 고정해 예고 없는 라이브러리 변경이 들어오지 않게 함 |
| 남은 일 | Supabase 대시보드에서 프로젝트 복구(Restore). 정지 후 90일이 지나면 대시보드 복구가 불가능해진다 |

## 5. 판단이 필요했던 지점

스펙만으로 결정할 수 없어 판단한 항목이다.

| 지점 | 선택 | 근거 |
|---|---|---|
| "All" 칩 제거 | 제거 | "나머지 7개를 비활성" 지시가 있었는데 기존 칩은 All 포함 9개였다. 스타일 칩 8개에서 하나를 빼면 정확히 7개라 All은 세지 않은 것으로 읽었다. 하나만 열린 상태에서 All은 동작할 수도 없었다. **이후 요청으로 복원함** |
| 초기 렌더 경로 | 필터를 거치도록 변경 | 화면 진입 시 전체 목록을 그리고 있어, 칩만 특정 태그로 표시해도 실제 목록은 전체가 나왔다. 칩과 목록이 어긋나 그대로 두면 잘못된 화면이 된다 |
| 빈 상태 문구 | 추가 | 요청에 없었으나, 빈 화면은 고장인지 데이터 없음인지 구분되지 않는다 |
| 매칭 없는 코디의 안내 | 추가 | 분석 버튼을 제거하면서 그 자리가 완전히 비었다 |
| `sold_out`을 NOT NULL로 | NOT NULL + 기본값 `false` | 기본값을 지정한 의도가 "값 없음 없이 시작"으로 읽혔다. 다른 두 컬럼은 `null` 처리를 명시한 것과 대비됐다. 화면이 참/거짓 두 가지만 다루면 된다 |
| 로딩 오버레이·에러 영역 제거 | 제거 | 분석 버튼 전용 UI라 버튼이 사라지면 절대 표시되지 않는 죽은 화면 요소가 된다 |
| 가격과 링크의 출처 | 같은 결과에서만 가져옴 | 서로 다른 검색 결과에서 가격과 링크를 짜맞추면 표시 가격과 실제 가격이 어긋날 수 있다. 링크가 구글인 것보다 나쁘다고 판단 |
| 마이그레이션 적용 시점 | 화면 수정과 함께 적용 | 작성만 요청받았으나, 새 컬럼을 조회하는 화면 코드가 들어간 상태에서 컬럼이 없으면 갤러리 전체가 빈 화면이 된다 |
| 관리자 화면 위치 | `templates/`로 이동, `/admin` 라우트 추가 | 기존 위치에서는 설정 파일 경로가 해결되지 않아 동작 자체가 불가능했다 |
| 검색 결과 선택 기준 | 품목 2점, 색 1점, 무신사는 필수 조건 | 색이 맞는 다른 품목보다 색이 틀린 같은 품목이 낫다. 품목이 어긋나면 아예 다른 옷이 된다 |
