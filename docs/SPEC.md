## 화면 구조

```
하단 탭 3개로 이동한다. 상단에는 서비스명만 둔다.

[사용자]
├─ 홈 탭 → 코디 피드       진입점. 검색 없음
│   └─ 코디 상세          핵심 화면
│       └─ 외부 몰        추적 종료 (새 탭)
├─ 저장함 탭              로그인 필요
│   └─ 코디 상세          재진입
└─ 프로필 탭              키·몸무게·사이즈·선호 핏 (전부 선택 입력)
    ├─ 비로그인이면 로그인/회원가입 화면
    ├─ 공지사항 → /notices
    └─ 개인정보처리방침 (자리만, 링크는 나중에)

[운영] /admin
├─ 코디 업로드 + AI 분석
├─ 공개 상태 관리
└─ 매칭 근거 큐레이션
```

**사용자 화면은 5개다.** 필터 확장과 검색은 여전히 제외한다.

### 레이아웃 기준

모바일 우선이다. 기본 스타일이 폰 화면이고, 넓은 화면에서는 **앱 폭 480px 로 가두어 가운데 정렬**한다. 바깥 여백은 `#000`, 앱 영역은 `#0a0a0a` 로 둔다.

| 항목 | 값 |
|---|---|
| 피드·저장함 그리드 | 2열 고정 (모바일·데스크톱 동일) |
| 카드 이미지 비율 | 3:4 |
| 하단 탭 | `position: fixed`, 높이 약 60px + `env(safe-area-inset-bottom)` |
| 입력 글자 크기 | 16px 이상 (그 미만이면 iOS 가 입력 시 화면을 확대한다) |

폭이 고정이라 미디어쿼리는 `hover` 판정 하나만 남는다.

### PWA

`static/manifest.json` — `display: standalone`, 테마 `#0a0a0a`, 아이콘 192·512 (`maskable` 포함). 홈 화면에 추가하면 브라우저 UI 없이 뜬다. iOS 는 `apple-mobile-web-app-*` meta 로 대응한다. **아이콘은 현재 플레이스홀더**이며 같은 경로에 덮어쓰면 교체된다.

로그인·프로필은 2026.09.14에 추가했다. 핏 불확실성이 망설임 요인의 76%로 나와 문제를 "이 옷이 나에게 어떻게 보일지 모른다"로 재정의했고, 체형 정보를 저장하려면 유저를 식별해야 하기 때문이다. 근거는 `DECISIONS.md` 참조.

### 화면별 검증 대상

| 화면 | 검증하는 가설 | 관련 지표 |
|---|---|---|
| 코디 피드 | 검색 없이도 탐색을 시작하는가 | 카드 선택률 |
| 코디 상세 | 코디 단위 대체 제안에 반응하는가 | 확인율, 코디당 클릭 수 |
| 저장함 | 레퍼런스 수집처를 대체하는가 | 저장률, 재방문율 |

## 데이터 구조

### 테이블

```
pinterest_looks                    코디
  id, image_url, style_tag, created_at
  is_public     ← 공개 여부. 기본값 true
        │
        │  looks_items_match       연결 (다대다)
        │    id, look_id, item_id
        │    original_type   ← 원본 아이템 유형 (브랜드명 제외)
        │    match_reason    ← 매칭 근거 한 줄
        │    UNIQUE(look_id, item_id)
        ↓
musinsa_items                      국내 대체 상품
  id, product_name, price, purchase_url, image_url
  product_key   ← 'musinsa:5909913' 형태, UNIQUE
  sold_out      ← 기본값 false

search_cache                       검색어 → 상품 캐시
  query(PK), item_id, hit_count
  RLS 켜짐 + 정책 없음 = Edge Function 전용

user_profiles                      유저별 체형 정보
  user_id(PK) → auth.users, ON DELETE CASCADE
  height, weight, photo_path               전부 null 허용
  size_alpha     ← XS~XXL        size_numeric  ← 90~110
  preferred_fit  ← 슬림핏/레귤러핏/세미오버핏/오버핏/상관없음
  허용값은 CHECK 가 아니라 comment on column 으로 남긴다
  created_at, updated_at                   updated_at 은 트리거가 갱신
  RLS 켜짐 + 정책 4개 (auth.uid() = user_id)

saved_looks                        유저가 저장한 코디
  id, user_id → auth.users, look_id → pinterest_looks
  UNIQUE(user_id, look_id)
  RLS 켜짐 + 정책 4개 (auth.uid() = user_id)
```

### 유저 데이터의 RLS

`user_profiles`, `saved_looks` 는 SELECT·INSERT·UPDATE·DELETE 네 작업 모두 `auth.uid() = user_id` 조건이다. 본인 데이터만 읽고 쓸 수 있다.

기존 3개 테이블은 이번 범위 밖이며 `README.md` 의 「배포 전 필수 조치」에 남아 있다.

### original_type과 match_reason을 연결 테이블에 둔 이유

**상품의 속성이 아니라 코디와 상품 사이 관계의 속성이다.**

같은 상품이 여러 코디에 매칭될 수 있고, 그때 "원본 사진 속 어떤 옷을 대체하는가"와 "왜 이 상품인가"는 코디마다 달라진다. 상품 쪽에 두면 한 코디의 근거가 다른 코디에도 딸려가 사실과 어긋난다.

`product_key`는 반대로 상품 고유 값이라 `musinsa_items`에 둔다. 구매 링크에 요청마다 바뀌는 추적 파라미터가 붙어 URL만으로는 식별할 수 없기 때문이다.

### 저장하지 않는 것

| 항목 | 이유 |
|---|---|
| 원본 아이템의 브랜드명·가격 | 레퍼런스에 링크가 없어 정확도 확보 불가 + 특정 브랜드 지목은 저작권 리스크 확장 |
| 코디 재현 총액 | 파생값. `sold_out = false`인 아이템의 `price` 합으로 계산 |
| 원본 이미지 파일 | 자체 저장하지 않고 출처 URL을 임베드 |

## 기능 명세

### 코디 피드

| 항목 | 내용 |
|---|---|
| 트리거 | 사이트 진입, 필터 칩 선택 |
| 조회 조건 | `is_public = true`인 코디만 조회한다 |
| 표시 | 2열 그리드. 코디 이미지(3:4) + 재현 총액대(만원 단위 내림) |
| 표시하지 않음 | 스타일명 (필터 칩과 중복), 검색창 |
| 필터 | 데이터가 있는 태그만 자동 활성. 없는 태그는 `disabled` + `cursor: not-allowed` |
| 초기 상태 | `activeTag = 'all'` |
| 예외 | 활성 태그에 코디가 0건이면 "준비 중인 스타일이에요" 안내 |

**필터 활성 여부를 하드코딩하지 않는다.** `allLooks`를 `style_tag`로 집계해 계산한다. 데이터가 늘거나 줄어도 화면이 자동으로 맞는다.

### 코디 상세

| 항목 | 내용 |
|---|---|
| 트리거 | 피드 또는 저장함에서 코디 카드 선택 |
| 입력 | 코디 ID, 사용자 식별자, 진입 경로, 진입 시각 |
| 표시 순서 | 원본 이미지 → 재현 총액 → 아이템 카드 3~5개 |
| 총액 블록 | 라벨 "이 코디, 국내 아이템으로" + 금액. 품절 제외 시 "품절 N개 제외" 표기 |
| 아이템 카드 | 상품 이미지, 상품명, 판매처·가격, **매칭 근거 한 줄** |
| 저장 버튼 | 상단 하트. 토글. `saved_looks` 테이블 (로그인 필요) |
| 표시하지 않음 | 원본 브랜드명·가격, AI 분석 버튼 |

**계측**

- 상세 진입 이벤트
- 매칭 결과 영역이 **뷰포트 진입 + 일정 시간 체류** 시 확인 이벤트 (단순 노출 아님)

**렌더링 규칙**

- `match_reason`이 `null`이거나 빈 문자열이면 해당 줄을 그리지 않는다
- 빈 문자열이 아니라 `null`로 저장한다 (빈 줄 방지)

**품절 처리**

- `opacity: 0.45`, 상품명 옆 "(품절)"
- 구매 링크 비활성화
- **목록 위치는 유지한다.** 아래로 내리면 코디 구성 순서가 깨진다
- 총액은 판매 중인 아이템 기준으로 산출하고 그 기준을 표기한다

### 아이템 구매 이동

| 항목 | 내용 |
|---|---|
| 트리거 | 아이템 카드 또는 구매 버튼 클릭 |
| 입력 | 코디 ID, 아이템 ID, 판매처, URL, 사용자 식별자, **클릭 순번**, 시각 |
| 처리 | ① 품절이면 중단 후 안내<br>② 클릭 이벤트 기록 (순번 포함)<br>③ **동일 세션·동일 코디에서 서로 다른 아이템의 2번째 클릭이면 코디 완성 시도 이벤트 추가 기록**<br>④ 제휴 링크면 파라미터 부착<br>⑤ 새 탭으로 이동 |
| 결과 | 원래 화면 유지. 이동한 아이템은 방문 표시 |

**③이 북극성 지표를 만드는 지점이다.** "서로 다른 아이템"이라는 조건이 반드시 필요하다. 같은 아이템을 두 번 누른 것은 완성 시도가 아니다.

**새 탭으로 여는 이유**: 현재 탭에서 이동하면 유저가 돌아오지 않는다. 코디 단위 재현이 목적이므로 나머지 아이템을 이어서 볼 수 있어야 한다.

### 코디 저장

| 항목 | 내용 |
|---|---|
| 트리거 | 상세 화면 저장 버튼 클릭 |
| 입력 | 코디 ID, **인증된 사용자 ID**, 저장 시각 |
| 처리 | ① 로그인 확인 ② 저장 여부 확인 ③ 없으면 `saved_looks` 추가, 있으면 삭제(토글) ④ 이벤트 기록 |
| 결과 | 버튼 상태 전환, "저장했어요" 토스트, 저장함 즉시 반영 |
| 정렬 | 최근 저장이 앞 (`created_at desc`) |

**예외 처리**

- **비로그인 상태에서 저장을 시도하면** 저장하지 않고 "로그인하면 저장할 수 있어요" 안내 후 로그인 화면으로 보낸다
- 원본 URL 무효·코디 비공개 전환 시 **목록에서 삭제하지 않고** "현재 볼 수 없는 코디" 안내를 표시한다. 저장은 "나중에 다시 보겠다"는 약속이므로 임의 삭제하지 않는다
- 저장 실패 시 버튼 상태 복원 및 재시도 안내

**localStorage 이관** — 로그인 이전에 로컬에 저장해 둔 목록이 있으면 첫 로그인 시 `saved_looks` 로 옮긴다. **로컬 원본은 지우지 않고** `saved_looks_migrated_at` 플래그로 재이관만 막는다(「자동 삭제를 하지 않는다」 원칙). 이관이 전부 실패하면 플래그를 남기지 않아 다음 로그인에 다시 시도한다.

### 저장함

| 항목 | 내용 |
|---|---|
| 트리거 | 하단 저장함 탭 |
| 표시 | 2열 그리드. 이미지(3:4) + 총액대 |
| 빈 상태 | "아직 저장한 코디가 없어요" + "코디 보러가기" 버튼 |
| 비로그인 | "로그인하면 저장한 코디를 볼 수 있어요" + "로그인하기" 버튼 |

피드와 같은 카드를 쓴다. 모바일 폭에서는 2열이 이미 한 화면에 여러 개를 보여준다.

### 로그인 / 회원가입

| 항목 | 내용 |
|---|---|
| 트리거 | 프로필 탭(비로그인), 비로그인 저장 시도, 비로그인 저장함 접근 |
| 입력 | 이메일, 비밀번호 |
| 처리 | Supabase Auth. **비밀번호는 Supabase 가 해시로 보관한다.** 앱은 평문을 저장하지 않는다 |
| 세션 | `onAuthStateChange` 로 로그인·로그아웃·토큰 갱신을 모두 받는다. 새로고침 후에도 유지 |
| 결과 | 로그인 성공 시 피드로. 헤더가 PROFILE 로 바뀐다 |
| 예외 | 자격 증명 오류·중복 가입·짧은 비밀번호·요청 과다를 우리말 문구로 안내 |

**이메일 확인** — 프로젝트 설정에서 껐다. 로컬·화면 공유 시연이 목적이고, 기본 SMTP 한도로 발표 중 로그인이 막히는 상황을 만들 수 없다. 켜져 있는 환경에서는 "확인 메일을 보냈습니다" 안내가 나간다.

### 프로필

| 항목 | 내용 |
|---|---|
| 트리거 | 하단 프로필 탭. 비로그인이면 로그인 화면으로 보낸다 |
| 입력 | 키(cm), 몸무게(kg), 알파벳 사이즈, 숫자 사이즈, 선호 핏 — **전부 선택 입력** |
| 처리 | `user_profiles` 에 upsert. 가입 시 트리거로 행을 미리 만들지 않고, 처음 저장할 때 생긴다 |
| 저장 규칙 | 빈 입력은 `null`. 0 이나 빈 문자열로 두면 "입력했는데 0"과 구분되지 않는다 |
| 표시 | 로그인 계정(이메일), 공지사항·개인정보처리방침 링크, 로그아웃 버튼 |
| 범위 밖 | 사진 업로드 (`photo_path` 컬럼만 미리 둠) |

**사이즈를 두 칸으로 나눈 이유** — 브랜드마다 표기 기준이 달라 유저가 기억하는 쪽이 다르다. 한 칸을 강요하면 "M인데 100이기도 한" 상황에서 무엇을 넣을지 막힌다. 둘 중 하나만 골라도 된다.

**선호 핏** — "평소 즐겨 입는 핏이 있다면 알려주세요". 지금은 저장만 하고 다른 기능에서 쓰지 않는다.

비워둬도 서비스를 쓰는 데 지장이 없다. 입력을 강제하면 가입 직후 이탈한다.

| 표시 | 코디별 작성 진행률 |
| 저장 | 빈 입력은 `null`로. 변경된 행만 저장 |

**매칭 근거 작성 기준**

실루엣·소재·색상·기장 중 **최소 하나를 명시한다.**

- ❌ 비슷한 느낌의 자켓
- ⭕ 오버핏 실루엣과 워싱 톤이 유사

## AI 분석 (Edge Function)

`supabase/functions/analyze-look/index.ts`

```
① lookId 없으면 pinterest_looks 생성
② 이미 분석된 코디면 저장된 결과 반환 (force로 우회)
③ extractItems() — GPT-4o Vision
     통제 어휘 사용, temperature 0
     "{색상} {핏} {품목}" 검색어 조립
④ resolveItem() 반복
     search_cache 조회 → 적중 시 외부 API 건너뜀
     findProduct() — SerpApi google_shopping → 무신사 직링크
     musinsa_items upsert + search_cache 기록 + 매칭 연결
```

**중요**

- 브라우저는 OpenAI·SerpApi를 직접 호출하지 않는다. 키는 Supabase 시크릿에만 있다
- **유저 화면에서 이 함수를 호출하지 않는다.** 운영 화면 전용이다
- 재분석은 해당 코디의 연결만 끊고 상품은 보존한다. 상품은 캐시 재사용 대상이다

**검색 결과 선택 기준**: 품목 2점, 색 1점, 무신사는 필수 조건. 색이 맞는 다른 품목보다 색이 틀린 같은 품목이 낫다.

**가격과 링크는 같은 검색 결과에서만 가져온다.** 서로 다른 결과에서 짜맞추면 표시 가격과 실제 가격이 어긋난다.
