## 🔒 UI · 화면

### 다크 테마, 이미지 중심 레이아웃

유저가 핀터레스트에서 유입되므로 **이미지가 주인공**이다. UI 색이 튀면 코디 사진이 죽는다. 배경은 어둡게, 텍스트는 최소, 포인트 컬러는 저장 버튼 하나 정도로 유지한다.

### 검색창을 제공하지 않는다

**이 서비스가 푸는 문제가 "검색어를 만들지 못한다"이다.** 검색창은 그 문제를 유저에게 되돌려준다. 탐색은 둘러보기로만 가능하게 한다.

### 무한 스크롤을 사용하지 않는다

탐색량은 늘지만 구매 결정을 지연시킨다. 북극성 지표가 "코디 완성 시도"이므로 훑는 행동이 아니라 들어가는 행동을 유도해야 한다.

### 원본 아이템의 브랜드명·가격을 표시하지 않는다

두 가지 이유가 겹친다.

- 레퍼런스 출처에 상품 링크가 없거나 해외 직구몰로 연결되어 **정확한 확인이 불가능하다**
- 특정 브랜드 상품을 지목한 대체 안내는 이미지 사용보다 **확장된 저작권 리스크**를 발생시킨다

대신 코디 재현 총액을 표시해 원본과의 비교 없이도 예산 판단이 가능하게 한다.

### 정보 밀도를 낮춘다

타깃이 패션 입문자다. 전문 용어를 화면에 쓰지 않고, 카드는 이미지 + 최소 정보로 구성한다.

### 매칭 근거를 반드시 함께 표시한다

문제 정의 ③(대체품이 분위기를 유지하는지 판단할 기준이 없다)에 대응하는 요소다. **이것이 없으면 일반 상품 목록과 구분되지 않는다.**

값이 `null`이면 해당 줄을 그리지 않는다. 빈 문자열이 아니라 `null`로 저장한다.

## 🔒 기능 범위

### 유저 화면에서 AI를 호출하지 않는다

수동 큐레이션이 MVP의 전제다. 매칭 정확도가 검증 목적에 미달했고, 결과가 부정확하면 유저는 "AI가 부족하다"가 아니라 **"이 서비스가 별로다"로 판단한다.**

운영 화면(`/admin`)의 분석 기능은 **데이터 생성 경로이므로 유지한다.**

### 매칭 근거는 사람이 작성한다

"좋은 매칭 근거란 무엇인가"를 정의하지 못한 상태에서 자동화하면 AI 출력을 평가할 기준도 없다. 사람이 작성한 근거가 이후 자동화의 정답 데이터가 된다.

### 로그인·마이페이지·필터 확장을 만들지 않는다

검증에 기여하지 않는 화면이다. 화면이 적을수록 각 화면이 무엇을 검증하는지 명확해진다.

### 아래 기능은 제외한다

| 기능 | 근거 |
|---|---|
| AI 착샷 | 대형 플랫폼 다수 제공 + 실사용 결과 디자인 치환 수준에 그쳐 목적 미달성 + RICE 최하위 |
| 개인화 추천 | 취향 예측은 "번역"이 아니다 |
| 광고 우선 노출 | 큐레이션 중립성 훼손. 우리가 기존 서비스의 한계로 지적한 문제와 동일 |

**새 기능 제안 시 판단 기준**: "이것이 해외 코디를 국내 아이템으로 옮기는 일에 해당하는가."

## 🔒 데이터 · 구현

### 원본 이미지는 자체 저장하지 않고 출처 URL을 임베드한다

저작권이 플랫폼이 아니라 **원 촬영자와 브랜드**에 있다. 플랫폼 API를 사용해도 해결되지 않는다.

임베드 방식은 원본 삭제 시 이미지가 깨지므로, **원본 URL이 유효하지 않은 코디는 공개 상태로 전환할 수 없도록** 운영 규칙으로 통제한다.

### 자동 삭제를 하지 않는다

재분석 시 "연결되지 않은 상품은 불필요"로 판단해 삭제하는 로직이 있었고, 캐시 도입 후 재사용 대상 자산까지 삭제되는 사고가 발생했다.

> **외부 데이터에 의존하는 구조에서 자동 삭제는 위험하다. 삭제 대신 비활성 표시로 처리한다.**

이 원칙은 유저 데이터에도 적용된다. 저장한 코디의 원본이 무효가 되어도 목록에서 삭제하지 않고 안내를 표시한다.

### 품질 미달 데이터는 삭제하지 않고 비공개 처리한다

AI 자동 매칭 결과가 원본과 일치하지 않아(13건 중 정확 0건) 해당 코디 5건을 유저 화면에서 제외했다. 그러나 삭제하지 않았다. AI 매칭의 현재 한계를 보여주는 유일한 실측 근거이므로, 덮어쓰면 이 기록을 재현할 수 없다.

이는 「자동 삭제를 하지 않는다」 원칙의 연장이다. 품질이 낮다는 이유로 데이터를 지우면, 나중에 무엇이 왜 낮았는지 확인할 방법이 사라진다.

### 외부 API 키는 반드시 서버 측에 둔다

브라우저로 전송되는 모든 코드는 사용자가 볼 수 있다. **프론트엔드에 "숨겨둔 파일"이라는 개념은 존재하지 않는다.**

과거 OpenAI 키가 `config.js`에 평문으로 노출된 상태였다. 현재는 Edge Function 경유로 변경했다.

### 필터 활성 여부를 하드코딩하지 않는다

데이터를 집계해 계산한다. 코디가 늘거나 줄어도 화면이 자동으로 맞아야 한다.

### 상태의 출처를 하나로 유지한다

과거 필터 활성 상태를 버튼 클래스로, 화면 전환을 `display` 속성으로 관리해 **DOM이 상태를 들고 있었다.** 현재는 `activeTag` 변수 하나만 보고 화면을 다시 그린다.

### 가격과 링크는 같은 검색 결과에서만 가져온다

서로 다른 결과에서 짜맞추면 표시 가격과 실제 상품 가격이 어긋난다. **링크가 부정확한 것보다 가격이 어긋나는 편이 나쁘다.**

## 🔒 계측

지표를 정의했으면 **명세에 계측이 들어가야 한다.** 처리 로직에 이벤트 기록이 없으면 구현되지 않고, 그러면 지표를 볼 수 없다.

| 규칙 | 이유 |
|---|---|
| 매칭 결과 확인은 **뷰포트 진입 + 체류**로 센다 | 단순 노출로 세면 스크롤만 지나가도 카운트된다. "확인율이 낮으면 노출 위치를 의심한다"는 판단 기준이 작동하지 않는다 |
| 아이템 클릭에 **순번**을 기록한다 | 코디당 클릭 수가 1에 가까울 때 어떤 카테고리가 먼저·많이 클릭되는지 봐야 원인을 진단할 수 있다 |
| 2번째 클릭에서 **코디 완성 시도**를 별도 기록한다 | 북극성 지표. "서로 다른 아이템"이라는 조건이 반드시 필요하다 |
| 외부 몰은 **새 탭**으로 연다 | 현재 탭 이동 시 유저가 돌아오지 않는다. 코디 단위 재현이 목적이므로 나머지 아이템을 이어서 볼 수 있어야 한다 |

## 🔒 프로세스

### 검증 속도가 프로덕션 품질보다 우선한다

가설 검증용 프로토타입이다. 코드가 검증 결과에 따라 폐기되거나 크게 바뀔 수 있다.

**테스트 주도 개발을 적용하지 않는다.** 테스트 작성에 시간을 쓰면 정작 검증할 것을 만들지 못한다.

### 보안 조치는 의도적으로 보류했다

세 테이블에 RLS가 꺼져 있고 `/admin`에 인증이 없다. **키를 확인한 누구나 데이터를 수정·삭제할 수 있다.**

| 구분 | 내용 |
|---|---|
| 판단 | MVP 검증 이후로 보류 |
| 근거 | 로컬·화면 공유로만 시연하며 외부 배포 계획이 없다. RLS는 기본값이 전면 차단이라 읽기 정책을 함께 만들어야 하고, 관리자 화면이 같은 키를 쓰고 있어 인증 도입이 선행되어야 한다 |
| 위험 | 매칭 판정 데이터는 이 서비스의 유일한 통제권 확보 축이다. 단순 보안 문제가 아니라 전략의 근간이 훼손될 수 있는 문제다 |

**배포 전 필수 조치**

- `pinterest_looks`, `looks_items_match`, `musinsa_items`에 RLS 적용
- anon 키는 SELECT만 허용
- `/admin`에 Supabase Auth 기반 인증 추가
- 쓰기는 인증된 사용자 또는 Edge Function으로 제한

## 🔄 재검토 예정

### 수동 큐레이션 vs 유저 이미지 업로드

| 구분 | 내용 |
|---|---|
| 현재 판단 | 큐레이션 유지 |
| 근거 | ① 텍스트 검색 4회 튜닝 결과 오차가 해소되지 않고 자리만 이동 — 비용이 아니라 구조적 한계<br>② 실패가 유저에게 직접 노출되어 서비스 신뢰를 훼손<br>③ 입문자 타깃과의 정합성 — 업로드는 "이 코디를 찾겠다"는 의도가 선행되어야 한다 |
| 재검토 시점 | **인터뷰 H10 판정 후** |
| 판단 기준 | 유저가 "내가 찜한 바로 그 코디"를 원하면 업로드 필요. "이런 분위기의 코디"를 원하면 현행 유지 |

### 기술 스택

| 구분 | 내용 |
|---|---|
| 현재 | Flask(HTML 서빙만) + Supabase + 바닐라 JS |
| 선택 경위 | **초기 학습 환경에 따른 선택이며 기술적 판단은 아니었다** |
| 알려진 한계 | 코디 상세에 URL이 없어 공유·새로고침·뒤로가기 불가. **공유는 Referral 지표에 해당하므로 구조적 결함이다.** 전역 변수 + `innerHTML` 렌더링은 화면이 늘면 관리가 어려워진다 |
| 재검토 시점 | **인터뷰 종료 후.** 문제 정의가 확정되면 재구축 검토 |
| 유의 | 재구축해도 Supabase 데이터는 재사용한다 |

### 코디당 매칭 아이템 수

| 구분 | 내용 |
|---|---|
| 명세 | 3~5개 |
| 현재 | 평균 2.6개 (코디 15건, 매칭 39건) |
| 영향 | 북극성 지표(2개 이상 클릭)는 성립하나, 코디 완성 경험은 약하다 |
| 재검토 시점 | 매칭 근거 입력 완료 후 |

### 스타일 필터 확장

| 구분 | 내용 |
|---|---|
| 현재 | 데이터가 있는 3개 태그만 활성 (긱시크·아메카지·고프코어) |
| 유의 | 코디가 늘면 자동으로 활성화된다. 코드 수정 불필요 |
| 재검토 시점 | 코디 50건 이상 시 테마 섹션 도입 검토 |
